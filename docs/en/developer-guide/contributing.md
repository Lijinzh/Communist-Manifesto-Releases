# Contribution and validation

The contribution workflow preserves user data, limits mutation scope, and makes every conclusion traceable to a test or physical evidence.

<!-- section:s002 -->
## Before starting

1. Read the target repository `AGENTS.md`, specifications, and current release handoff.
2. Run `git status --short --branch` and identify existing changes plus untracked files.
3. Fetch remotes and inspect divergence; do not overwrite user changes or force-push.
4. Define acceptance criteria and whether hardware, a browser, or a native platform builder is required.

<!-- section:s003 -->
## Documentation changes

- The root entries are only `README.md` and `README.en.md`.
- Canonical documents live under `docs/zh-CN/` and `docs/en/` with identical relative Markdown paths.
- Each page pair uses the same ordered `<!-- section:... -->` IDs.
- Compatibility pages are generated by `scripts/sync_docs.py`; do not edit their bodies.
- After changes, run:

```powershell
uv run --no-project python scripts/sync_docs.py
uv run --no-project python scripts/sync_docs.py --check
uv run --no-project python -m unittest discover -s tests -v
git diff --check
```

<!-- section:s004 -->
## AutoClipboard or firmware changes

- Use the main repository `uv --project AutoClipboard` environment.
- Run the unit, contract, smoke, and compile checks related to the change.
- When hardware is available and identity is unique, firmware changes require a V3 build, validated app-only package, validated flash, serial readback, and BLE/IMU live smoke.
- Do not use PlatformIO upload to bypass package validation, write bootloader/partitions, or erase NVS/SPIFFS.

<!-- section:s005 -->
## Website changes

- Keep the Gitee mainland-primary and GitHub fallback downloads on exact versioned assets.
- Update automated tests and cache-version parameters with page changes.
- Validate desktop and mobile viewports, console health, primary navigation, one real interaction, and the live cache-busted page.
- Screenshots, temporary scripts, and reports are not committed by default.

<!-- section:s006 -->
## Commit and publish

1. Stage only task-related files; do not use `git add -A`.
2. Inspect the staged diff and run `git diff --check`.
3. Create a commit with a clear scope.
4. Use fast-forward and non-force push for normal synchronization.
5. After a formal Release, run `git sync-release-mirrors` and verify GitHub/Gitee main, tags, assets, and anonymous downloads.

<!-- section:s007 -->
## Evidence vocabulary

- `implemented`: source implementation exists.
- `fixture`: controlled test data passed.
- `full-download`: a complete public asset was downloaded and verified.
- `physical-live`: real device or real platform interaction passed.

Do not use lower evidence to claim a higher result, and do not extend one operating system result to another.
